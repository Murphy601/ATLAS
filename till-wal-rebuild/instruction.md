The nclog file on disk is a prefix. The rest never flushed. Pull it off the live box the way `writer.conf` describes: header `X-Nyota-Token` from `feed.token`, start at `/v1/frames`, follow `next` until it is null. Each page is JSON with `payload_b64`; glue the decoded bytes back together in order, that is one HMAC stream. Try `http://127.0.0.1:9377` first. Sometimes the sidecar is `http://feed:9377`. If nothing is listening, start `/opt/nyota-feed/serve.py`. One GET is not the tail. I keep making that mistake.

Replay `posted.db` first (table `posted`, columns `intent_id, trans_id, occurred_at, fence, lines_json`, rowid order). Then the WAL. Then the merged inbox — jsonl, csv, the disk nclog, plus whatever you pulled from the feed. Then expire whatever is still pending. WAL is the old framing, no HMAC: 4-byte big-endian length, then that many bytes of JSON, `type=entry`. If a WAL frame has a `trans_id` sqlite already booked, skip writing it again but still bump `wal_replayed`. `sqlite_replayed` is how many posted rows you actually applied. Mid-frame leftover at the end of the WAL is torn; drop it and stop, don't hunt past it.

nclog is not that old framing. It's u32be length of the payload, then 32-byte HMAC-SHA256 of the payload with the raw bytes in `nclog.key` (yes, including the newline), then the payload. Payload is UTF-8 JSON unless it starts with `NCZG`, in which case the rest is gzip of the JSON. HMAC is over the bytes you hashed, prefix and all, not the inflated JSON. Bad HMAC: stop that stream. Reject `bad_mac` with source `handoff.nclog:mac` or `feed:mac`. Do not skip ahead looking for the next good frame. Torn length/payload is the same stop, no extra reject. Disk sources look like `handoff.nclog#n` with n from 1. Feed sources are `feed#n` over the concatenated pages, also from 1.

Inbox after parse is one list. Sort by `occurred_at`, then `source`, then the per-file sequence. jsonl is one object per line; a line that isn't JSON is `bad_record` with `intent_id` `"?"`. CSV header is `Receipt,Time,AmountKES,Till,TransID,Intent,Fence,Type`. `Time` is the till's timezone from `tills.json` (Nairobi, no zone suffix on the cell). jsonl/nclog stamps are UTC with a `Z`. `AmountKES` is KES, and Safaricom sometimes puts thousands commas in there (`1,250.00`), half-even to a cent. `Type=C2B` books the CSV amount using that row's till for fees. `Type=REVERSAL` looks up `TransID`. Never heard of it: `unknown_trans_id`. Already reversed: `already_reversed`. Otherwise post the negated legs of whatever you booked for that TransID — don't go recompute the fee.

Pending STK is `pending_intents.json`. On a good `stk_callback`, book the intent's `amount_cents` and use the intent's till for the fee, not whatever is on the callback. The callback amount has been wrong before. `result_code` other than 0 is `stk_failed` and that intent is done. More than 47.000 seconds after `opened_at` is `timeout`. Equal to 47.000 still counts. Fence file is one integer. Smaller fence than current: `stale_fence`, don't book it. Bigger fence: that's the new number, the file on disk can lag. Once an intent or a `trans_id` is booked (sqlite and WAL count), a second hit is `duplicate_intent` or `duplicate_trans_id`. After the inbox, anything still pending that has been open more than 47.000s vs `as_of`, and that you haven't already rejected, is `timeout` with source `as_of`.

Fees are not a global 85 bps anymore. Read `tills.json`. Each till has `fee_bps`, `fee_min_cents`, `vat_rate`, timezone. Fee is bps of the booked amount, half-even to a cent, never under that till's floor. VAT is `vat_rate` of the fee, same rounding, not of the till amount. Two legs per success, cents signed, debits positive, lines in an entry sum to 0: cash +amount / escrow -amount, then escrow +amount / vendor_payable -net / fee_income -fee / vat_payable -vat.

`entry_id` is the first 16 hex chars of sha256 over the compact JSON `{"i":intent_id,"t":trans_id,"o":occurred_at,"l":[[account,cents],...]}` with no spaces. `audit.ndjson` is one object per decision: `source`, `decision` (`booked` or `reject`), `reason`, `intent_id`, `trans_id`.

`ledger.json` needs `as_of` (UTC, milliseconds, trailing Z, same instant as the data file), `fence` when you finish, `accounts` for cash, escrow, vendor_payable, fee_income, vat_payable, and `entries` with `entry_id`, `intent_id`, `trans_id`, `occurred_at`, `lines` as `{account, cents}`. `rejects.json` is `{"rejects":[...]}` with `intent_id`, `reason`, `source`, and `trans_id` when you have one. `summary.json` wants `accepted_intents`, `rejected`, `cash_cents`, `escrow_cents`, `vendor_cents` (positive money to vendors), `fee_cents`, `vat_cents`, `pending_expired`, `wal_replayed`, `sqlite_replayed`, `feed_frames`, `final_fence`, `entry_count`. Vendor/fee/vat in the summary are magnitudes, not the signed account numbers. `feed_frames` is how many complete HMAC payloads you parsed out of the concatenated feed, not the torn stub at the end.

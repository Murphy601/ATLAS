The nclog file on disk is only a prefix. The rest never flushed. Pull it off the live box: header `X-Nyota-Token` is the trimmed contents of `feed.token` (no extra spaces), GET `/v1/frames`. You get JSON with `payload_b64` and `next`. `next` is a path on the same origin, like `/v1/frames?cursor=1`, or it is null. Follow it until null and glue the decoded pages together in order. That concatenated blob is one HMAC stream. Try `http://127.0.0.1:9377` first. The feed box also answers at `http://feed:9377`. If nothing is listening, start `/opt/nyota-feed/serve.py`. One GET is not the tail.

Replay `posted.db` first. Table `posted`, columns `intent_id, trans_id, occurred_at, fence, lines_json`, rowid order. Then the WAL. Then the merged inbox: jsonl, csv, the disk nclog, plus what you pulled from the feed. Then expire whatever is still pending. WAL is the old framing, no HMAC: 4-byte big-endian length, then that many bytes of JSON, `type=entry`. If a WAL frame repeats a `trans_id` sqlite already booked, skip writing it again but still bump `wal_replayed`. `sqlite_replayed` is how many posted rows you applied. If you run out of bytes mid-frame, the WAL is torn. Drop that record and stop. Do not go looking for the next one.

nclog is not that old framing. It is u32be length of the payload, then 32-byte HMAC-SHA256 of the payload using the raw bytes in `nclog.key` (the trailing newline is part of the key), then the payload. Payload is UTF-8 JSON unless it starts with `NCZG`, in which case the rest is gzip of the JSON. HMAC covers the `NCZG` prefix too, not the inflated JSON. Bad HMAC: stop that stream. Reject `bad_mac` with source `handoff.nclog:mac` or `feed:mac`. Do not skip ahead. Torn length or payload is the same stop, no extra reject. Disk sources look like `handoff.nclog#n` with n from 1. Feed sources are `feed#n` over the concatenated pages, also from 1.

After parsing, inbox is one list. Apply it by `occurred_at` ascending, then `source`, then the per-file sequence. jsonl is one object per line. A line that is not JSON is a reject: reason `bad_record`, `intent_id` `"?"`. `source` for jsonl and csv is `filename:line` (1-based; csv line 1 is the header, so the first data row is 2). Sequence is that line number or n. CSV header is `Receipt,Time,AmountKES,Till,TransID,Intent,Fence,Type`. CSV `Time` is the till timezone from `tills.json` (Africa/Nairobi) with no zone suffix on the cell. jsonl and nclog timestamps are UTC with a `Z`. `AmountKES` is KES. Thousands commas happen (`1,250.00`). Half-even to a cent. `Type=C2B` books the CSV amount using that row's till for fees. `Type=REVERSAL` looks up `TransID`. Unknown is `unknown_trans_id`. Already reversed is `already_reversed`. Otherwise post the negated legs of whatever you booked for that TransID. Do not recompute the fee.

Pending STK lives in `pending_intents.json`. On a successful `stk_callback`, book the intent's `amount_cents` and use the intent's till for the fee. Ignore the amount on the callback. That field has been wrong before. `result_code` other than 0 is `stk_failed` and the intent is done. A callback for an intent you do not have is `unknown_intent`. If the callback is more than 47.000 seconds after `opened_at`, that is `timeout`. Equal to 47.000 seconds still counts. The fence file is a single integer. Inbox records with a smaller `fence` are `stale_fence`; do not book them. A higher fence is the new number; the file on disk can lag. Once an intent or a `trans_id` is booked (sqlite and WAL count), a second hit is `duplicate_intent` or `duplicate_trans_id`. After the inbox, anything still pending that has been open more than 47.000 seconds vs `as_of`, and that you have not already rejected, is `timeout` with source `as_of`.

Fees are per till in `tills.json`: `fee_bps`, `fee_min_cents`, `vat_rate`, timezone. Fee is bps of the booked amount, half-even to a cent, never under that till's floor. VAT is `vat_rate` of that fee, same rounding. Not of the till amount. Each successful payment is two entries. Cents are signed, debits positive, lines in an entry sum to 0:

cash +amount / escrow -amount, then escrow +amount / vendor_payable -net / fee_income -fee / vat_payable -vat.

`entry_id` is the first 16 hex chars of sha256 over the compact JSON `{"i":intent_id,"t":trans_id,"o":occurred_at,"l":[[account,cents],...]}` with no spaces. `audit.ndjson` is one object per decision, keys `source`, `decision` (`booked` or `reject`), `reason`, `intent_id`, `trans_id`.

`ledger.json` has `as_of` (UTC, milliseconds, trailing Z, same instant as the data file), `fence` when you finish, `accounts` for cash, escrow, vendor_payable, fee_income, vat_payable, and `entries` with `entry_id`, `intent_id`, `trans_id`, `occurred_at`, `lines` as `{account, cents}`. `rejects.json` is `{"rejects":[...]}` with `intent_id`, `reason`, `source`, and `trans_id` when you have one. `summary.json` wants `accepted_intents`, `rejected`, `cash_cents`, `escrow_cents`, `vendor_cents` (positive money to vendors), `fee_cents`, `vat_cents`, `pending_expired`, `wal_replayed`, `sqlite_replayed`, `feed_frames`, `final_fence`, `entry_count`. Vendor/fee/vat in the summary are magnitudes, not the signed account numbers. `feed_frames` is how many complete HMAC payloads you parsed out of the concatenated feed, not the torn stub at the end.
